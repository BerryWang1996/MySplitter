# v1.0.3 Production Readiness Notes

## Sensitive Configuration

MySplitter now treats datasource password loading as an explicit mode choice.

- `passwordSource: plain`: keeps passwords exactly as written in `mysplitter.yml`. This is intended for local development and quick demos where convenience is more important than secret isolation.
- `passwordSource: environment`: resolves passwords from system properties or environment variables. Use either `password: ${MYSQL_PASSWORD}` or `passwordEnv: MYSQL_PASSWORD`.
- `passwordSource: legacy-rsa`: keeps compatibility with existing RSA-encrypted configuration. This is a migration mode, not production-grade secret management.

`enablePasswordEncryption: true` still maps to `legacy-rsa` for backward compatibility, but new deployments should prefer `passwordSource`.

Production guidance:

- Do not commit production passwords to YAML.
- Prefer platform-managed secrets such as Kubernetes Secrets, Vault, KMS-backed secret injection, CI/CD secret variables, or Spring environment placeholders.
- Treat legacy RSA config encryption as obfuscation only. The application still needs plaintext credentials in memory to initialize the real datasource.

## YAML Loading

Configuration loading uses SnakeYAML safe construction and manually maps YAML primitives into MySplitter config objects. This avoids arbitrary Java type construction while preserving the existing YAML shape.

## Transaction Boundaries

MySplitter local transactions are intentionally limited to one physical connection. When `autoCommit=false`, the first routed/admin connection becomes the transaction boundary for that logical connection. If later SQL would require a different physical route, MySplitter fails fast with `SQLException` instead of attempting a best-effort multi-connection commit.

Production guidance:

- Keep one logical transaction on one routed database/node.
- Use the upcoming distributed transaction modes when cross-database atomicity is required.
- The planned path is XA first for standards-based cross-brand transactions, then AT, TCC, and Saga for scenarios where XA is not available or not appropriate.
- See `docs/distributed-transaction-roadmap.md` for the distributed transaction roadmap.

## Statement Batch Routing

`Statement.addBatch(...)` can route individual SQL statements to different physical statements. MySplitter now keeps the logical add order, executes each routed physical batch, and merges update counts back in the same order that callers added SQL to the batch.

## Default SQL Classification

The default read/write parser is intentionally conservative. It routes plain `SELECT` statements to readers after stripping leading ordinary comments, but routes lock-sensitive or ambiguous SQL to writers, including:

- `SELECT ... FOR UPDATE`
- `SELECT ... FOR SHARE`
- `LOCK IN SHARE MODE`
- vendor hint comments such as `/*+ ... */` and `/*! ... */`
- `WITH`, `SHOW`, `EXPLAIN`, `CALL`, and other non-plain-SELECT statements
