# v1.0 Upgrade Guide

This guide is for users moving from the `0.9.x` line to the `1.0.x` baseline.

## Supported Baseline

| Area | v1.0.x baseline |
| --- | --- |
| Java | Java 8+ |
| Spring Boot starter | Spring Boot 2.7.x |
| Primary connection pool | HikariCP |
| Demo baseline | Spring Boot 2.7.18 |
| Configuration format | YAML through `classpath:` or `file:` resources |

See `docs/v1.0-compatibility-matrix.md` for the full support matrix.

## Required Changes

### Java Runtime

`v1.0.x` raises the minimum Java baseline to Java 8.

Before upgrading, make sure the application runtime, build plugins, and CI agents use Java 8 or newer.

### Spring Boot Starter

The starter now targets Spring Boot `2.7.x` and ships both auto-configuration metadata paths:

- `META-INF/spring.factories`
- `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`

Existing Boot 2.7 applications should continue using the starter normally. Spring Boot 3.x and Jakarta migration are planned for a future major version and are not part of the `1.0.x` compatibility promise.

### Datasource Configuration Loading

The starter resolves configuration from Spring `Resource` locations instead of direct filesystem paths.

Supported examples:

```yaml
spring:
  datasource:
    mysplitter:
      configuration-file: classpath:mysplitter.yml
```

```yaml
spring:
  datasource:
    mysplitter:
      configuration-file: file:/opt/app/mysplitter.yml
```

This is the preferred replacement for deployments that previously depended on an expanded filesystem path inside the application package.

### Connection Pool Policy

HikariCP is the primary documented and regression-validated pool for `v1.0.x`.

Recommended shared configuration:

```yaml
mysplitter:
  common:
    dataSourceClass: com.zaxxer.hikari.HikariDataSource
```

Historical pools such as Druid, DBCP2, C3P0, BoneCP, and Tomcat JDBC remain compatibility options through the reflective configuration model, but they are no longer described as the primary operational baseline.

## Behavior Changes To Validate

### Logical Connection Reuse

The logical connection model now reuses physical connections per routed node. Transactional reads are pinned to writer connections while the transaction is active.

Application checks to run after upgrade:

- Verify transaction commit and rollback paths.
- Verify read-after-write behavior inside transactions.
- Verify code that changes connection attributes such as auto-commit, read-only, catalog, schema, type map, isolation level, and holdability.

### Filters

`filters` now run for every routed SQL, including reused connections and transaction-pinned routes.

If a filter performs logging, metrics, auditing, or access control, expect it to observe every routed statement instead of only newly opened physical connections.

### Failover And Health State

Health tracking is separated from selector behavior, and failover attempts are bounded. A node that fails during a single acquisition path is not immediately retried again in that same path as an ill-node fallback.

Application checks to run after upgrade:

- Verify failover behavior with one reader unavailable.
- Verify writer failure handling in the application's expected deployment topology.
- Confirm alert handlers are idempotent because repeated failures can still produce repeated health transitions over time.

## Release Validation

Use the repository release gate as the canonical local sign-off command:

```powershell
.\scripts\release-gate.ps1
```

On Unix-like shells:

```bash
./scripts/release-gate.sh
```

The release gate runs core module verification, starter tests, the dedicated regression module, demo compile checks, and release packaging.

Docker is not required for the baseline release gate because the H2 routing integration path is always on. Docker-backed MySQL Testcontainers coverage remains supplemental and runs when Docker is available.

## Known Limits

- Spring Boot 3.x compatibility is not included in `1.0.x`.
- Micrometer metrics and Actuator integration are planned for `1.1.0`.
- Broader CI and integration matrix expansion is planned for `1.2.0`.
- The demo is a runnable sample, not the recommended production architecture.
