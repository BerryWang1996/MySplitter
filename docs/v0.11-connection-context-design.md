# v0.11 Connection Context Design

## Purpose

This document defines the target logical connection model for the `v0.11` refactor.
The goal is to make connection reuse, transaction behavior, and statement execution
deterministic before larger routing and health-state refactors begin.

## Current Problems

The current implementation still has prototype-era connection semantics:

- `MySplitterConnectionProxy` resolves a physical connection from SQL execution time instead of
  owning a stable logical connection context.
- `MySplitterStatementProxy` can switch the underlying physical connection between statements.
- Connection state is replayed through reflection-style standby execution instead of explicit state.
- A transaction can span multiple independently opened physical connections without a clear pinning rule.
- Read operations inside a transaction may drift away from writer nodes.
- `ConnectionHolder` and `StatementHolder` are append-only lists, not route-aware registries.

These behaviors make transaction semantics hard to reason about and hard to test.

## Design Goals

- One logical `Connection` owns one `ConnectionContext`.
- Physical connections are reused by route key inside the same logical connection.
- Routed SQL never opens an unrelated default connection.
- Transaction mode is explicit and stable.
- Reads inside a transaction always use writer or integrate nodes.
- Connection state propagation is explicit, not reflection based.
- Statement objects stay attached to the physical connection selected for the current route.

## Core Model

### New Objects

#### `ConnectionContext`

Owns all mutable state for one logical connection.

Suggested fields:

- `boolean closed`
- `boolean autoCommit`
- `boolean readOnly`
- `int transactionIsolation`
- `String catalog`
- `String schema`
- `int holdability`
- `Map<String, Class<?>> typeMap`
- `Properties clientInfo`
- `Integer networkTimeoutMillis`
- `Executor networkTimeoutExecutor`
- `String username`
- `String password`
- `Map<RouteKey, Connection> routedConnections`
- `Connection administrativeConnection`
- `List<RouteKey> acquisitionOrder`

Notes:

- `autoCommit` defaults to `true`.
- `routedConnections` stores one physical connection per route key.
- `administrativeConnection` is a compatibility bridge for route-neutral JDBC methods such as
  `getMetaData()` and `createClob()`. It must never be reused for routed SQL execution.
- `acquisitionOrder` defines deterministic commit, rollback, savepoint, and close order.

#### `RouteKey`

Represents the physical route chosen for a statement.

Suggested fields:

- `String databaseName`
- `String nodeGroup`
- `String nodeName`

Rules:

- `nodeGroup` is one of `readers`, `writers`, or `integrates`.
- Route keys must be unique within one logical connection.

#### `ConnectionState`

Explicit snapshot of logical connection settings that can be applied to a physical connection.

Suggested responsibilities:

- Store current logical settings.
- Apply all relevant settings to a newly opened physical connection.
- Update already-open physical connections when JDBC setters are called.

### Holder Changes

`MySplitterConnectionHolder` and `MySplitterStatementHolder` should stop behaving as append-only lists.

Target behavior:

- `MySplitterConnectionHolder` becomes a route-aware registry backed by `Map<RouteKey, Connection>`.
- `MySplitterStatementHolder` becomes a registry keyed by `RouteKey` and statement identity.
- Both holders should expose deterministic iteration order.

## Lifecycle Rules

### 1. Logical Connection Creation

When `MySplitterDataSource.getConnection(...)` is called:

- Create `MySplitterConnectionProxy`.
- Create one empty `ConnectionContext`.
- Do not open any physical connection yet.

### 2. Route-Neutral JDBC Methods

Methods such as `getMetaData()`, `nativeSQL()`, `createClob()`, `createBlob()`, `createArrayOf()`,
and similar JDBC operations may require a physical connection before any routed SQL is executed.

Rule:

- Resolve a lazily created `administrativeConnection` through `getDefaultConnection()`.
- Apply current `ConnectionState` to it immediately.
- Include it in `commit()`, `rollback()`, `close()`, and savepoint handling if it has been created.
- Never use it as the target connection for routed SQL.

This preserves current compatibility while keeping SQL routing deterministic.

### 3. Routed SQL Execution

For `prepareStatement`, `prepareCall`, `executeQuery`, `executeUpdate`, `execute`, and batch entry methods:

1. Parse database route from the SQL.
2. Parse operation type from the rewritten SQL.
3. If `autoCommit` is `false`, coerce `read` operations to `writer` routing.
4. Ask the manager for a `RouteKey` plus `DataSourceWrapper`.
5. Reuse the existing physical connection for that `RouteKey` if present.
6. Otherwise open a new physical connection, apply `ConnectionState`, store it in the context,
   and record the route in acquisition order.

Result:

- The first routed statement defines the physical connection for that route.
- Later statements on the same route reuse the same physical connection.

### 4. Statement Creation

`Statement` and `PreparedStatement` behavior must follow the selected route.

Rules:

- `PreparedStatement` and `CallableStatement` are bound to one physical connection at creation time.
- `Statement` resolves its route per SQL execution, but it must cache one physical `Statement`
  per `RouteKey` and reuse it when the same route is selected again.
- `Statement.getConnection()` always returns the logical connection proxy.

## Transaction Rules

### Transaction Mode

Transaction mode is active when `setAutoCommit(false)` has been called and not reverted to `true`.

Behavior in transaction mode:

- All routed SQL goes to `writers` or `integrates`.
- Reads are never sent to `readers`.
- One physical writer connection is reused per target database route.
- `commit()` and `rollback()` operate on every opened physical connection in deterministic order.

This is the transaction pinning rule for `v0.11`.

### `setAutoCommit(false)`

Effects:

- Update logical state.
- Apply the setting to every already-open physical connection.
- Do not eagerly open new route connections.

### `setAutoCommit(true)`

Effects:

- First commit the current physical connections if the driver requires it through normal JDBC semantics.
- Clear transaction-mode routing behavior.
- Keep already-open physical connections reusable until the logical connection is closed.

### `commit()`

Rules:

- Iterate over routed connections and the administrative connection in acquisition order.
- Commit every opened physical connection exactly once.
- If multiple commits fail, throw the first exception and add later failures as suppressed exceptions.

### `rollback()`

Rules:

- Same iteration and exception-merging behavior as `commit()`.
- Roll back only already-open physical connections.

### Savepoints

Rules:

- Savepoints apply only to already-open physical connections.
- A logical savepoint stores one real savepoint per physical connection.
- If no physical connection exists yet, savepoint operations should fail fast with a clear `SQLException`
  instead of materializing an arbitrary routed connection.

This avoids implicit routing decisions that JDBC callers cannot predict.

## State Propagation Rules

The following methods should update `ConnectionState` first, then apply changes to all opened
physical connections:

- `setAutoCommit`
- `setReadOnly`
- `setCatalog`
- `setTransactionIsolation`
- `setTypeMap`
- `setHoldability`
- `setClientInfo`
- `setSchema`
- `setNetworkTimeout`

The following methods should read from `ConnectionState` when no physical connection exists yet:

- `getAutoCommit`
- `isReadOnly`
- `getCatalog`
- `getTransactionIsolation`
- `getHoldability`
- `getClientInfo`
- `getSchema`
- `getNetworkTimeout`

This removes the need for `MySplitterStandByExecuteHolder` in connection state handling.

## Data Source Manager Changes

`MySplitterDataSourceManager` should stop returning raw `Connection` objects for routed SQL.

Target change:

- Replace `getConnection(MySplitterSqlWrapper ...)` with a route resolution method that returns
  a route selection result.

Suggested result object:

- `RouteSelection`
  - `RouteKey routeKey`
  - `DataSourceWrapper dataSourceWrapper`
  - `String rewrittenSql`
  - `String operation`

Responsibilities:

- Keep routing and failover inside the manager.
- Keep connection reuse inside `ConnectionContext`.

## Failure Handling Rules

- If opening a new physical connection fails, only the failing route is retried.
- Existing physical connections already stored in the context remain valid.
- Failover must not discard unrelated route connections owned by the same logical connection.
- If a node is marked ill during route selection, the context should retry selection, not rebuild itself.

## Implementation Sequence

### Phase 1

- Introduce `ConnectionContext`, `ConnectionState`, and `RouteKey`.
- Teach `MySplitterConnectionProxy` to use the context instead of `MySplitterStandByExecuteHolder`.

### Phase 2

- Refactor `MySplitterStatementProxy` to resolve and reuse physical statements by route.
- Convert holders from list-based storage to route-aware registries.

### Phase 3

- Change `MySplitterDataSourceManager` to return route selection results instead of opened connections.
- Preserve existing filter execution and failover behavior during the transition.

### Phase 4

- Add focused tests for transaction pinning, read-after-write consistency, savepoints, and multi-route commit order.

## Test Matrix For This Refactor

- Auto-commit read routes to reader.
- Auto-commit write routes to writer.
- Transaction read routes to writer.
- Same route reuses the same physical connection.
- Two databases in one logical transaction reuse one writer connection per database.
- Commit touches every opened physical connection once.
- Rollback touches every opened physical connection once.
- Savepoint creation fails before any physical connection exists.
- Connection setters applied before first SQL are visible on newly opened physical connections.

## Out Of Scope

These items belong to later milestones:

- Weight-model redesign
- Boot 2.7 or Boot 3 auto-configuration work
- Micrometer metrics
