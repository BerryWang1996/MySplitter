# v0.12 Routing And Health Design

## Purpose

This document records the current routing, health-state, and failover model that has already
landed during the `v0.12` refactor line.

The goal is to align source code, regression tests, and future work before `v1.0.0`
baseline upgrades begin.

## Landed Structure

The core routing path is now split into explicit layers instead of the original prototype-style
single manager flow.

Main objects:

- `MySplitterDataSourceRegistry`: stores route groups and all registered datasource nodes.
- `MySplitterDataSourceGroup`: owns one selector plus a unique node set for one
  `database + nodeGroup` combination.
- `MySplitterDataSourceHealthManager`: tracks ill-node versions, scheduled recovery, and
  version-safe healing decisions.
- `MySplitterDataSourceManager`: performs route planning, failover selection, filter execution,
  and connection opening.
- `MySplitterConnectionContext`: keeps logical-connection state, opened physical connections,
  and transaction-pinned routes.

## Routing Rules

### Route Planning

For routed SQL:

1. Resolve target database through the configured database router.
2. Rewrite SQL if the database manager returns a rewritten statement.
3. Parse operation through the read/write parser.
4. Coerce `readers` to `writers` when a transaction is active.
5. Reuse a pinned route for the same database when transaction pinning is already in effect.

### Connection Reuse

- One logical connection reuses one physical connection per `RouteKey`.
- Transaction-pinned reads reuse the writer route for the same database.
- Route-neutral JDBC operations still use the administrative/default connection path.

## Health Model

Ill-state tracking is version based.

Rules:

- `markIll(...)` stores a monotonically increasing failure version per selector/node pair.
- Scheduled recovery only heals the node if the scheduled version still matches the current one.
- Success-based recovery also uses version matching so stale recovery success cannot erase a newer failure.
- Health status is stored in concurrent maps rather than selector-local mutable lists.

## Failover Rules

### Current Bounded Behavior

One route/default-connection acquisition now uses a per-call candidate snapshot.

Rules:

- Healthy candidates are snapshotted first.
- A node that fails in the current acquisition path is removed from the local candidate list.
- The same node is not retried again immediately in the same call through the ill-node fallback path.
- Ill-node recovery only considers nodes that were not already tried and failed earlier in the same call.

This gives the current implementation a practical bounded-failover rule:

- each node is attempted at most once per acquisition path.

### Recovery Safety

If an ill node accepts a connection during recovery:

- the manager only keeps that connection if the node version still matches the version captured before the recovery attempt;
- otherwise the newly opened connection is closed and discarded as stale.

## Filter Execution Rules

- `DataSourceFilterAdvise` runs once per routed SQL.
- Reused routed connections do not bypass the filter chain.
- Transaction-pinned reads still execute filters even when the physical connection was already open.

## Verification Coverage

Current regression coverage includes:

- logical connection lifecycle and transaction pinning
- nullable connection-state replay
- abort semantics before first physical connection
- per-SQL filter execution
- concurrent health-state transitions
- stale scheduled recovery protection
- version-matched healing
- bounded failover for routed and administrative connection acquisition
