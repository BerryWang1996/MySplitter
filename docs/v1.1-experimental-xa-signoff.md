# v1.1 Experimental XA Signoff Checklist

`v1.1.0` should ship XA as an experimental MVP only. The default production path remains `transaction.mode: local`; `transaction.mode: xa` requires `mysplitter.experimental.xa.enabled=true`.

## Required Before Tagging

- Done: core module tests pass: `.\mvnw.cmd -q -pl mysplitter test`.
- Done: full regression module passes with Docker Desktop running: `.\mvnw.cmd -q -pl mysplitter-tests -am test`.
- Done: repo release gate passes: `powershell -ExecutionPolicy Bypass -File .\scripts\release-gate.ps1`.
- Done: `git diff --check` has no whitespace errors.
- Done: the compatibility matrix in `docs/v1.1-xa-compatibility-matrix.md` is current.
- Done: the operations notes in `docs/v1.1-xa-operations.md` are current.
- Done: release notes clearly state that XA is experimental and gated.
- Done: README links to the experimental XA docs without presenting XA as production-ready.

## XA Coverage Required For This MVP

- H2 routed XA lifecycle baseline: two routed branches commit and rollback through `MySplitterDataSource`.
- Non-XA datasource nodes are rejected during XA initialization.
- MySQL prepared branch file-log recovery covers commit and rollback.
- PostgreSQL prepared branch file-log recovery covers commit and rollback.
- PostgreSQL database-unavailable recovery failure leaves prepared file-log branches recoverable.
- Unit-level failure injection covers prepare, commit, rollback, recovery commit, recovery rollback, and recover-scan failures.
- XA gate tests prove default rejection and explicit development opt-in.

## Explicit Non-Production Caveats

- The embedded coordinator is process-local and does not provide multi-process fencing or leader election.
- There is no admin API yet for listing, retrying, or resolving in-doubt branches.
- Metrics and structured operational events are not implemented yet.
- Real database failure-injection coverage is intentionally narrow and should expand before production promotion.
- `memory` transaction logs are test-only; durable recovery requires `file` logs and stable resource ids.

## Promotion Criteria For A Later Release

- Admin visibility for recoverable, unresolved, committed, and rolled-back branches.
- Operational metrics and structured recovery logs.
- Documented manual recovery workflow for unresolved branches.
- More deterministic real-database failure injection, especially commit/rollback interruption scenarios.
- A reviewed support contract that states exactly which database brands, versions, and drivers are supported.
