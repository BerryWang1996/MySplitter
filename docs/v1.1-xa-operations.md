# v1.1 XA Operations Notes

`transaction.mode: xa` is implemented in the `1.1.0-SNAPSHOT` line, but remains behind the development gate `mysplitter.experimental.xa.enabled=true`. The current `v1.1.0` decision is to keep XA experimental and keep `transaction.mode: local` for production deployments.

## Configuration Shape

```yaml
mysplitter:
  transaction:
    mode: xa
    coordinator:
      type: embedded
      logStore: file
      logFile: ./target/mysplitter-xa.log
    recovery:
      enabled: true
      interval: 10s
```

Supported coordinator options in the current snapshot:

| Option | Supported values | Notes |
| --- | --- | --- |
| `transaction.coordinator.type` | `embedded` | The coordinator runs inside the MySplitter process. |
| `transaction.coordinator.logStore` | `memory`, `file` | `memory` is test-only for process restart recovery; `file` is required for durable recovery. |
| `transaction.coordinator.logFile` | File path | Required when `logStore: file`. Put it on durable storage and keep it process-local unless an external coordinator is introduced. |
| `transaction.recovery.enabled` | `true`, `false` | Starts a background recovery scan after datasource initialization. |
| `transaction.recovery.interval` | `10s`, `1m`, `1h` style values | Defaults to `10s` when omitted. |

## Recovery Behavior

- Each enlisted XA branch is logged with `globalTransactionId`, `resourceId`, `branchId`, branch status, and durable decision.
- Commit first prepares all branches, then records a global `COMMIT` decision, then commits each branch.
- Rollback records a global `ROLLBACK` decision, then rolls back branches in reverse enlistment order.
- Recovery only finishes a branch when the log has a durable `COMMIT` or `ROLLBACK` decision and the database reports the matching `Xid` from `XAResource.recover(...)`.
- Branches with `UNKNOWN` decisions remain unresolved; MySplitter does not guess.
- Branches whose resource is missing, whose recovered `Xid` is absent, or whose XA commit/rollback fails remain recoverable in the log.
- `XA_RDONLY` prepare results are recorded as completed branches and are not retried during recovery.

## Operational Requirements

- Every XA node must configure a real `xaDataSourceClass`; non-XA datasource nodes are rejected during initialization when XA mode is active.
- Use `file` log storage for any recovery validation. `memory` is useful for fast tests but cannot recover after process restart.
- Protect and retain the transaction log file until all recoverable branches are resolved. Deleting it can strand in-doubt database transactions.
- Keep resource ids stable. In the current design, resource ids come from the configured datasource node identity, so renaming nodes can prevent recovery from locating the original branch resource.
- PostgreSQL requires `max_prepared_transactions > 0`.
- MySQL legacy driver validation uses `useSSL=false` in Testcontainers under newer JDKs.

## Current Limits

- The embedded coordinator is process-local; multi-process coordination, fencing, and leader election are not implemented yet.
- Real-database failure injection is still limited. Unit tests cover state-machine failures, while Testcontainers currently proves prepared-branch recovery for MySQL/PostgreSQL and PostgreSQL database-unavailable recovery failure.
- Metrics, structured recovery events, and admin APIs for unresolved branches are still future work.
- `transaction.mode: xa` stays experimental for the `v1.1.0` MVP until these limits are addressed in a later support contract.
